# Contributing to Formato24

Useful contributions start with a clear problem. We welcome feedback, documentation improvements, testing observations, and focused changes to repositories that accept public contributions. Participation follows our [Code of Conduct](https://github.com/formato24-os/.github/blob/main/CODE_OF_CONDUCT.md).

## Choose the right contribution

| Work | How to contribute |
| --- | --- |
| This `.github` repository | Open an issue or a focused pull request for the profile, policies, templates, or validation tools. |
| Cocosite feedback | Describe a use case or reproducible alpha issue through [community issues](https://github.com/formato24-os/.github/issues/new/choose). See the [current scope](https://github.com/formato24-os/.github/blob/main/docs/COCOSITE.md). |
| Another public repository | Follow its README, license, contribution policy, and checks. |
| Private or proprietary implementation | Obtain maintainer approval and the applicable contribution terms before submitting source or requesting access. |

Public feedback is not a promise of a feature, source access, release date, or acceptance. A new project proposal does not join a monthly release cycle; Cocosite is the current priority.

## Before opening an issue

Search existing reports. Identify the affected project and version, explain the expected and actual behavior, and give the smallest useful reproduction. Separate a product limitation from a regression where possible.

For account or verification problems, name the failing step without sharing your email address, password, verification code, session cookie, or token. Redact screenshots and logs. For vulnerabilities, use the [security policy](https://github.com/formato24-os/.github/blob/main/SECURITY.md) rather than public issues.

## Prepare a pull request

1. Read the target repository's license and instructions. Do not assume Formato24 products are open source because this repository is public.
2. Discuss substantial changes before implementation. Fork or branch only where the repository's terms permit it.
3. Keep the change focused; update affected documentation and meaningful verification.
4. Credit sources and confirm that submitted code, text, and assets can be distributed under the target repository's terms.
5. Explain the problem, resulting behavior, checks performed, and any remaining limitations in clear English.

For `.github`, run the [validation commands](https://github.com/formato24-os/.github/blob/main/docs/validation.md) and inspect Markdown rendering. Shared policy links should use absolute URLs so they also work in other repositories. Keep status claims factual and distinguish implementation, testing, and public availability.

## Review

Draft pull requests are welcome where public contributions are accepted. Reviewers should give concrete feedback and distinguish required fixes from suggestions. Maintainers may request a smaller scope or additional evidence and make the final decision under [governance](https://github.com/formato24-os/.github/blob/main/GOVERNANCE.md). Response times depend on availability.

For usage questions, see [Support](https://github.com/formato24-os/.github/blob/main/SUPPORT.md).
